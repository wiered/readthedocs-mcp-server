# readdocs-mcp-server: инструменты, ресурс и слеш-команды

Документация по MCP-серверу `readthedocs-docs`: что делает каждый tool, как устроен поиск и как выбирать границы строк при `fetch`.

## Общая схема

1. **`index_readthedocs`** — скачать и проиндексировать дерево документации (HTML → текст в SQLite, чанки для FTS5, сущности Sphinx при наличии).
2. **`list_indexed_sources`** — узнать, какие корни (`source_base`) уже в базе и сколько страниц.
3. **Поиск** — `search` (по страницам), `search_in_file` (внутри одной страницы), `search_entities` (классы/методы и т.д.).
4. **Чтение** — **`fetch`** по URL-идентификатору из результатов поиска; при необходимости — срез по строкам `start`/`end`.
5. **Символы и граф** — `lookup_symbol`, `related_symbols`, `get_symbol_graph_stats`, плюс сущности: `get_entity`, `list_class_methods`, `get_entity_context`.
6. **Обзор страниц** — `list_documentation_pages` (список URL с оглавлением разделов).

Переменные окружения см. в [README](../README.md#environment-variables) (`READTHEDOCS_MCP_DB`, транспорт, хост/порт и т.д.).

## Инструменты (tools)

### `index_readthedocs`

Скачивает страницы под заданным URL (BFS в пределах корня документации), извлекает текст, строит чанки для полнотекстового поиска и сохраняет структурированные сущности (классы/методы), если разметка Sphinx это позволяет.

| Параметр | Описание |
|----------|----------|
| `seed_url` | Абсолютный `http`/`https` URL входа в документацию. |
| `max_pages` | Верхняя граница числа страниц (1–5000, по умолчанию 200). |
| `request_delay_sec` | Пауза между запросами, 0–30 с (по умолчанию 0.15). |
| `replace_source` | Если `true`, перед обходом удаляются данные по этому нормализованному корню. |

Ответ: `IndexStats` — корень, число загруженных/пропущенных, ошибки, путь к БД.

---

### `list_indexed_sources`

Список всех `source_base` в индексе с числом страниц и временем последней загрузки. Используйте значения `source_base` для **`search`**, **`search_entities`** и фильтров **`list_documentation_pages`**, чтобы ограничить область одним проектом документации.

---

### `search`

Полнотекстовый поиск по **чанкам** проиндексированных страниц (SQLite FTS5). См. раздел [Как устроен поиск](#как-устроен-поиск) ниже.

| Параметр | Описание |
|----------|----------|
| `query` | Строка запроса (не пустая). |
| `limit` | Число результатов, 1–100 (по умолчанию 15). |
| `source_base` | Необязательно: только один корень документации (как из `list_indexed_sources`). |

**Важно:** для глобального поиска на **одну страницу приходится не больше одного попадания** (лучший чанк по релевантности). Чтобы получить несколько фрагментов с **одной и той же** страницы, используйте **`search_in_file`**.

Каждый результат (`SearchResult`) содержит:

- `id` / `url` — канонический URL страницы (его же передают в `fetch` как `id`);
- `title` — заголовок страницы;
- `text` — короткий сниппет вокруг совпадения;
- `line` — **приблизительный** номер строки в полном тексте страницы (удобно для ориентира);
- `chunk_line_start` / `chunk_line_end` — диапазон строк **в пределах проиндексированного чанка** (1-based, inclusive), в котором лежит попадание; их удобно использовать как стартовую область для **`fetch(..., start=..., end=...)`**.

---

### `search_in_file`

Тот же FTS5, но запрос выполняется **только по одной странице** (`page_url`). Можно вернуть **несколько** попаданий с одного URL (разные чанки).

| Параметр | Описание |
|----------|----------|
| `page_url` | Абсолютный `http`/`https` URL страницы из индекса. |
| `query` | Строка запроса. |
| `limit` | 1–100. |

Используйте, когда уже знаете страницу (например, из TOC или прошлого `search`), но нужно найти все упоминания термина внутри неё.

---

### `search_entities`

Поиск по **структурированным сущностям** (таблица `doc_entities`: имена, сигнатуры, summary, тело сущности в FTS). Те же **многоступенчатые** FTS-запросы, что и для `search`, но индекс другой — ориентир на API-идентификаторы, классы и методы.

| Параметр | Описание |
|----------|----------|
| `query` | Строка запроса. |
| `kind` | Необязательно: `class` или `method`. |
| `source_base` | Ограничение одним корнем документации. |
| `limit` | 1–100. |
| `include_related` | Если `true`, в ответ подмешивается краткая связанная информация по графу (как для детальных вызовов). |

В результатах есть `entity_id` — его передают в **`get_entity`**.

---

### `get_entity`

Загрузка **одной** сущности по `entity_id` из результатов `search_entities`.

| Параметр | Описание |
|----------|----------|
| `entity_id` | Идентификатор из поиска сущностей. |
| `include_methods` | Для класса — подгружать методы (по умолчанию да). |
| `include_params` | Параметры функции/метода. |
| `include_notes` | Заметки, предупреждения, версии и т.д. |

Ответ: `entity` либо `null`, если записи нет.

---

### `get_entity_context`

Ищет **одну** подходящую сущность по строке `query` (как короткий путь «вопрос → один объект API») и возвращает её же структуру, что и `get_entity`, с упором на параметры и заметки.

| Параметр | Описание |
|----------|----------|
| `query` | Строка (например, имя символа или фраза из документа). |
| `kind` | Необязательно: `class` или `method`. |
| `include_notes` | По умолчанию `true`. |
| `source_base` | Ограничение корнем. |

---

### `list_class_methods`

Список методов класса по **`class_entity_id`** или по **`class_name`** (и опционально `source_base` для снятия неоднозначности).

---

### `lookup_symbol`

Точечный поиск символа в рамках **`source_base`** по строке **`symbol_name`** (как в документации: `Module.Class.method`). Возвращает страницу, якорь, диапазоны строк сущности, краткий **`context`** (срез текста страницы вокруг объявления: примерно несколько строк до и после диапазона сущности) и при необходимости связанные данные.

Поля `line_start` / `line_end` и `context_start` / `context_end` относятся к **тексту страницы** и помогают сориентироваться; для точного чтения фрагмента страницы используйте **`fetch`** с `start`/`end` (см. ниже).

---

### `related_symbols`

Соседи в **типизированном графе** рёбер: методы класса, базовые классы, типы параметров/возврата, ссылки и т.д.

| Параметр | Описание |
|----------|----------|
| `source_base` | Корень документации. |
| `symbol_name` | Имя символа (как для `lookup_symbol`). |
| `edge_types` | Необязательный список типов рёбер; допустимые значения: `has_method`, `inherits_from`, `returns`, `accepts_parameter_type`, `references`, `see_also`, `mentioned_in_note`, `mentioned_in_warning`, `only_valid_in`, `requires`, `use_instead`, `similar_to`, `converts_to`. |
| `direction` | `out`, `in` или `both`. |
| `limit` | 1–100 (по умолчанию 50). |

---

### `get_symbol_graph_stats`

Диагностика по графу для `source_base`: счётчики по типам рёбер, несопоставленные xref и прочее. Полезно при отладке индекса или качества извлечения ссылок.

---

### `list_documentation_pages`

Постраничный список URL с заголовками и древовидным оглавлением разделов (`toc`).

| Параметр | Описание |
|----------|----------|
| `source_base` | Фильтр по корню. |
| `url_contains` | Подстрока в URL. |
| `limit` | 1–500 (по умолчанию 200). |
| `offset` | Смещение для пагинации. |

---

### `fetch`

Загрузка **полного текста** одной проиндексированной страницы по **`id`** (это URL из полей `id`/`url` в результатах `search` и др.).

| Параметр | Описание |
|----------|----------|
| `id` | URL страницы в индексе. |
| `start`, `end` | Необязательно: **оба сразу** — нумерация строк **с 1**, **включительно** (`start` и `end` входят в срез). |

Поведение среза и советы — в разделе [Границы строк в `fetch`](#границы-строк-в-fetch).

Ответ `FetchResponse`: `text` (полный текст или срез), `total_lines` — число строк во **всём** теле страницы (при срезе это всё равно полное число строк до нарезки), `slice_start` / `slice_end` — фактически применённые границы после приведения к допустимому диапазону (если был срез).

## Как устроен поиск

### Индекс и ранжирование

- Текст страниц режется на **чанки** (с перекрытием; параметры подобраны так, чтобы длинные страницы покрывались несколькими фрагментами).
- Для `search` / `search_in_file` используется виртуальная таблица **FTS5** (`porter` + `unicode61`): стемминг и нормализация токенов, ранжирование **`bm25()`** — меньше значит лучше.
- Запросы к FTS не подставляются «как есть»: движок строит **несколько вариантов MATCH** (см. `fts_query`): сначала более строгий запрос (ключевые термы как обязательные AND, остальное как опциональный OR-блок), затем ослабление (один «якорный» термин), затем широкий fallback для длинных формулировок (OR по топ-токенам). Это снижает пустые ответы на естественных вопросах и шумных запросах.
- «Сильные» токены (длинные, с цифрами, `CamelCase`, подчёркивания и т.д.) чаще попадают в обязательную часть; общие слова из списка низкого сигнала (`documentation`, `example`, …) не должны «убить» recall, за счёт чего длинные вопросы могут переключаться в **free mode** с OR-fallback.

### `search` vs `search_in_file`

| | `search` | `search_in_file` |
|---|----------|------------------|
| Область | Весь индекс (или один `source_base`) | Одна страница (`page_url`) |
| Повторы с одного URL | Нет — **не больше одного результата на URL** | Да — несколько чанков с одной страницы |
| Когда использовать | Найти релевантные **страницы** | Углубиться в уже известную **страницу** |

### `search` vs `search_entities`

| | `search` | `search_entities` |
|---|----------|---------------------|
| Объект | Чанки обычного текста страниц | Записи о символах API (имя, сигнатура, summary, тело) |
| Когда | Общие темы, объяснения, гайды | Классы, методы, точные имена в духе Sphinx |

Практика: для «как настроить X» — чаще `search`; для «класс `FooBar`» — `search_entities` или `lookup_symbol`.

### Как формулировать запросы

- Для имён API используйте **точные идентификаторы** как в документации (`module.ClassName`, `snake_case`).
- Длинные вопросы на естественном языке допустимы: пайплайн сам ослабит AND-требования.
- Если пусто — сократите до 1–2 ключевых слов или перейдите на `search_in_file` по странице из оглавления.
- Всегда указывайте **`source_base`**, если в индексе несколько проектов — так меньше шума.

## Границы строк в `fetch`

### Правила

1. **Нумерация с 1**, обе границы **включительны**: строка `end` входит в результат.
2. Задать нужно **оба** параметра **`start` и `end`**, либо **ни одного** (тогда возвращается вся страница). Только одно из двух — ошибка валидации.
3. Максимальная длина среза: **5000 строк** за один вызов (`end - start + 1 ≤ 5000`).
4. Если `start` больше числа строк в документе, текст среза будет пустым, но метаданные страницы всё равно вернутся; `slice_start` / `slice_end` отражают запрошенные или сжатые границы (см. реализацию `slice_body_lines`).

### Откуда брать `start` и `end`

- Из **`search` / `search_in_file`**: поля **`chunk_line_start`** и **`chunk_line_end`** задают участок страницы, соответствующий найденному чанку — разумный первый срез для чтения совпадения без всей страницы.
- Поле **`line`** — **приблизительная** одна строка «центра» совпадения; можно взять окно вокруг неё (например ±50–200 строк), если чанк слишком узок или нужен контекст. Для длинных разделов комбинируйте несколько вызовов `fetch` с разными окнами.
- Из **`lookup_symbol`** / сущностей: **`line_start` / `line_end`** описывают объявление в тексте страницы — хорошая основа для среза; при необходимости расширьте диапазон вниз для примеров и пояснений.

### Когда что выбирать

| Ситуация | Рекомендация |
|----------|----------------|
| Нужен весь раздел / статья | `fetch(id)` без `start`/`end` (или несколько срезов, если ответ упирается в лимит 5000 строк). |
| Нужен только фрагмент из поиска | `start`/`end` = `chunk_line_start`/`chunk_line_end` из результата. |
| Нужен контекст вокруг совпадения | Расширьте диапазон от чанка или от `line`, следя за лимитом 5000 строк. |
| Очень длинная страница | Сначала `search_in_file`, затем точечные `fetch` по чанкам; не выгружайте десятки тысяч строк без необходимости. |

## Слеш-команды (MCP prompts)

Клиенты MCP могут показывать их как готовые шаблоны. Имя промпта — то, что часто вызывают как «команду».

### `index-docs`

Параметр: `seed_url`. Вставляет в чат инструкцию вызвать **`index_readthedocs`** с этим URL и по умолчанию обобщить результат индексации.

### `search-docs`

Параметр: `query`. Инструкция вызвать **`search`** (при необходимости с `source_base` из **`list_indexed_sources`**) и кратко резюмировать релевантные попадания с предложением, какой `id` загрузить дальше.

### `read-page`

Параметры: `id` (URL страницы), опционально `question`. Инструкция вызвать **`fetch`** для этого `id` и при наличии вопроса ответить по содержимому страницы.

---

## Быстрый типовой сценарий

1. `list_indexed_sources` — выбрать нужный `source_base`.
2. `search` с узким запросом и `source_base` (или `search_entities` для API).
3. По выбранному URL: при необходимости `search_in_file` для детализации по странице.
4. `fetch` с `start`/`end` из чанка или целиком без среза.
5. Для навигации по API: `lookup_symbol` / `related_symbols` / `get_entity`.
